# Withdraw hooks

Withdraw request lifecycle — initiate, cancel, finalize, plus reads for the pending queue.

Reach for **`useWithdraw`** first: it is the **high-level** entry point that takes
just `{ account, amount, receiver }` (amount in the **collateral token's decimals**)
and does the rest — it reads the subaccount's isolation, picks the right withdraw
path, builds the withdraw part, and scales the deallocate amount — so the UI never
branches on where the collateral sits or scales anything. `useInitiateWithdraw` and
the deallocate-and-initiate variant remain available for callers that already know
the isolation and want to drive one specific path, or need custom (multi-part /
cross-chain) withdraw parts.

## Import

```ts
import {
  // Reads
  useExpressWithdrawOptions,
  useExpressWithdrawStatus,
  useExpressWithdrawStatuses,
  useLastWithdrawRequestId,
  usePendingWithdrawRequests,
  useWithdrawRoute,
  useWithdrawRouteChoices,
  useWithdrawRequest,
  useWithdrawableTime,
  // Writes
  useWithdrawWithExpress,
  useWithdraw, // high-level entry point
  useInitiateWithdraw,
  useSimulateInitiateWithdraw,
  useRequestCancelWithdraw,
  useSimulateRequestCancelWithdraw,
  useFinalizeWithdrawRequest,
  useSimulateFinalizeWithdrawRequest,
} from "@symmio/trading-react";
```

## Express-aware withdrawal

Use `useWithdrawRoute` to prepare a route before the user confirms, then pass that exact route to
`useWithdrawWithExpress`. This keeps fee and timing details shown in the UI bound to the signed option submitted on-chain.
The existing `useWithdraw` hook remains the classic-only API.

```tsx
import {
  isExpressWithdrawPayoutComplete,
  useExpressWithdrawStatus,
  useWithdrawRoute,
  useWithdrawWithExpress,
} from "@symmio/trading-react";

function WithdrawPanel({ account, amount, receiver }) {
  const route = useWithdrawRoute({
    user: account,
    amount,
    receiver,
    query: { enabled: amount > 0n },
  });
  const withdraw = useWithdrawWithExpress({ account });
  const requestId = withdraw.data?.requestId;
  const status = useExpressWithdrawStatus({
    user: account,
    requestId: requestId ?? 0n,
    query: { enabled: requestId !== undefined && withdraw.data?.route.kind === "express" },
  });

  const submit = () => {
    if (!route.data) return;
    withdraw.mutate({ amount, receiver, preparedRoute: route.data });
  };

  const paid = status.data ? isExpressWithdrawPayoutComplete(status.data) : false;
  // Render route.data, submit, status.data, and paid.
}
```

### User-selectable Auto, Classic, and Express routes

Use `useWithdrawRouteChoices` when the interface should default to the SDK recommendation but allow an explicit choice.
It performs at most one Express options request for the exact account, amount, and receiver. `recommended` preserves the
existing automatic behavior; `available` contains Classic plus every valid offer returned by the service.

```tsx
const routes = useWithdrawRouteChoices({
  user: account,
  amount,
  receiver,
  query: { enabled: amount > 0n },
});
const automaticWithdraw = useWithdrawWithExpress({ account });
const classicWithdraw = useWithdraw({ account });

function submit(method: "auto" | "classic" | "standard") {
  if (!routes.data) return;

  if (method === "classic") {
    classicWithdraw.mutate({ amount, receiver });
    return;
  }

  const route =
    method === "auto"
      ? routes.data.recommended
      : routes.data.available.find(
          (candidate) => candidate.kind === "express" && candidate.option.optionTypeName === "STANDARD",
        );

  if (!route || (method !== "auto" && route.kind !== "express")) return;
  automaticWithdraw.mutate({ amount, receiver, preparedRoute: route });
}
```

Reset an explicit selection when the account, amount, receiver, or chain changes. Display only Express choices actually
returned by `available`; if a selected signed offer disappears or expires, disable submission instead of silently using
another route. `useWithdrawRoute` remains the smaller API for automatic-only interfaces.

The default router chooses classic immediate withdrawal when the account holds at least the requested available balance and its cooldown is already satisfied. Otherwise it
prefers `SAME_TX`, then `STANDARD`, and falls back to classic cooldown withdrawal if the service is disabled or cannot
return a usable option. `CUSTOM` accounts retain the classic deallocate-and-initiate path. Opt into `WINDOWED` or strict
service failure explicitly:

```ts
useWithdrawRoute({
  user: account,
  amount,
  receiver,
  policy: {
    optionPriority: ["WINDOWED", "SAME_TX", "STANDARD"],
    fallback: "error",
  },
});
```

<Callout type="warning">
  Express v1 is same-chain only. For a `STANDARD` option, Core `FINALIZED` means the provider recovered its funds—not
  that the receiver was paid. `useExpressWithdrawStatus` keeps polling until provider `PROCESSED`, and
  `isExpressWithdrawPayoutComplete` applies the correct option-aware rule.
</Callout>

### Lower-level hooks

- `useExpressWithdrawOptions` requests signed, non-expired service offers for one exact account, amount, receiver, and
  affiliate. It never retries automatically because `POST /options` creates service records.
- `useExpressWithdrawStatus` polls every three seconds by default. It continues through `NOT_FOUND` while indexing and
  through `STANDARD` + `FINALIZED`; it stops after proven payout or cancellation, suspension, or local failure.
- `useExpressWithdrawStatuses` accepts active on-chain `WithdrawRequest` values, keeps only requests belonging to the
  configured Express provider, and polls each status independently. Use it with `usePendingWithdrawRequests` to restore
  provider progress after a page refresh.
- `useWithdrawRoute` owns safe automatic ordering and classic fallback. Its returned `WithdrawRoute` is the preview
  object accepted by the mutation.
- `useWithdrawRouteChoices` returns the unchanged automatic recommendation plus Classic and all current Express choices
  for interfaces that expose route selection.
- `useWithdrawWithExpress` waits for the mined receipt, decodes the exact `WithdrawInitiated` request id, and returns
  `{ hash, receipt, requestId, route }`.

Each hook exports its matching parameter and return aliases:
`UseExpressWithdrawOptionsParameters` / `UseExpressWithdrawOptionsReturnType`,
`UseWithdrawRouteParameters` / `UseWithdrawRouteReturnType`,
`UseWithdrawRouteChoicesParameters` / `UseWithdrawRouteChoicesReturnType`,
`UseExpressWithdrawStatusParameters` / `UseExpressWithdrawStatusReturnType`, and
`UseExpressWithdrawStatusesParameters` / `UseExpressWithdrawStatusesReturnType`,
`UseWithdrawWithExpressParameters` / `UseWithdrawWithExpressReturnType`. The mutation additionally exports
`WithdrawWithExpressVariables` and `WithdrawWithExpressResult`.

After success, `useWithdrawWithExpress` invalidates account balance info, balance-of, withdrawable time, pending requests,
all withdrawal requests, and last request id. It removes every cached Express offer, prepared route, and route-choice list
for that account so a signed offer cannot be accidentally reused.

## `useWithdraw` — high-level withdraw

Pass the subaccount `account` to the hook, then `mutate` with a **minimal input**:
`{ amount, receiver }`, with `amount` in the **collateral token's decimals** (e.g. 6
for USDC). You do not pass `isolationType`, build `parts`, or scale anything — the
hook reads the subaccount's `SubAccountIsolationType` via `useSubAccount` (deduped by
react-query with any other `useSubAccount` on the same key, e.g. one driving a balance
display), builds the classic same-chain withdraw part,
scales the deallocate amount, and dispatches on the isolation, which determines
**which balance the funds are in** and therefore which underlying action runs:

| `isolationType`                    | Where the funds sit | What runs                                                                      |
| ---------------------------------- | ------------------- | ------------------------------------------------------------------------------ |
| `CUSTOM` (cross-margin)            | allocated (margin)  | `deallocateAndInitiateWithdraw` — deallocate **and** initiate in one atomic tx |
| `MARKET` / `MARKET_DIRECTION` (VA) | available           | `initiateWithdraw` — initiate only                                             |

A `CUSTOM` subaccount holds its collateral in the **allocated** balance, so it must
first be deallocated into the available balance; that path batches both legs into a
single transaction. Account-layer balances are `1e18`-scaled regardless of the
collateral token's decimals, so the hook scales your collateral-decimals `amount` to
the 18-decimal amount the deallocate leg needs. The VA modes already hold their funds
in the **available** balance, so they only initiate the request.

```tsx
import { useWithdraw } from "@symmio/trading-react";

const { mutate } = useWithdraw({ account });

// amount in the collateral token's decimals (6-dec USDC → 1 USDC):
mutate({ amount: 1_000000n, receiver });
```

On success it invalidates the subaccount's balance reads (`balanceInfo`, `balanceOf`), pending and complete withdrawal
reads, last request id, and withdrawable time. It also removes cached Express offers and route preparations because the
submitted Classic request makes those signed choices stale. On the `CUSTOM` path the SDK fetches a fresh Muon uPnL
signature for the deallocate leg unless you
pass one as `upnlSig`. Backed by the core [`withdrawAuto`](../symmio-contract#withdrawauto--high-level-entry-point)
action; reach for `useInitiateWithdraw` / the deallocate-and-initiate variant when
you already know the isolation or need custom withdraw parts.

## Lifecycle overview

1. **Initiate** — `useInitiateWithdraw` submits a withdraw request. Enters the delayed queue.
2. **Wait** — `useWithdrawableTime` tells the UI when the request becomes claimable.
3. **Finalize** — `useFinalizeWithdrawRequest` claims the funds after the delay.
4. **Cancel** (optional) — `useRequestCancelWithdraw` cancels a pending request.

Each write has a paired `useSimulate*` — see [Simulate then write](../concepts/simulate-then-write).

## Reads

### `useLastWithdrawRequestId`

Id of the most recent request for an account.

```ts
const lastId = useLastWithdrawRequestId({ account });
```

### `usePendingWithdrawRequests`

Every queued (not yet claimable) request for an account.

```ts
const pending = usePendingWithdrawRequests({ account });
```

Pair the pending contract read with `useExpressWithdrawStatuses` to recover active
Express progress after remounting or refreshing the page:

```tsx
const pending = usePendingWithdrawRequests({ user: subAccount });
const express = useExpressWithdrawStatuses({
  requests: pending.data ?? [],
  enabled: pending.data !== undefined,
});

for (const entry of express.entries) {
  // entry.request is the on-chain request; entry.status is service progress.
}
```

Classic requests and requests for a different provider are excluded. The hook
uses the same payout-aware polling policy as `useExpressWithdrawStatus`, including
continuing through `STANDARD` + `FINALIZED` until provider `PROCESSED`.

### `useWithdrawRequest`

Details for one specific request.

```ts
const request = useWithdrawRequest({ account, requestId });
```

### `useWithdrawableTime`

Timestamp when a queued request becomes claimable. Bind to a countdown / claim button.

```ts
const { withdrawableAt, isReady } = useWithdrawableTime({ requestId });
```

## Writes

<Callout type="info">
  Every write on this page is [relayable](/core/gasless/relayable-writes): pass `gasless: true` in the mutation
  variables to sign it as an InstantLayer operation and let the relayer pay the gas. See [Gasless
  hooks](/react/gasless).
</Callout>

### `useInitiateWithdraw` / `useSimulateInitiateWithdraw`

Submit a withdraw request directly, without the isolation dispatch. This is the
**initiate-only** leg — the right call for a `MARKET` / `MARKET_DIRECTION` (VA)
subaccount whose funds are already in the available balance, or when you drive the
`deallocateAndInitiateWithdraw` variant yourself for a `CUSTOM` subaccount. Prefer
[`useWithdraw`](#usewithdraw--isolation-aware-withdraw) when you don't want to
branch on isolation.

```ts
const simulation = useSimulateInitiateWithdraw({ account, amount });
const mutation = useInitiateWithdraw();
```

### `useRequestCancelWithdraw` / `useSimulateRequestCancelWithdraw`

Cancel a pending request.

```ts
const mutation = useRequestCancelWithdraw();
mutation.mutate({ account, requestId });
```

### `useFinalizeWithdrawRequest` / `useSimulateFinalizeWithdrawRequest`

Claim funds after the delay expires.

```ts
const mutation = useFinalizeWithdrawRequest();
mutation.mutate({ account, requestId });
```
