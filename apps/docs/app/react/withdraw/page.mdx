# Withdraw hooks

Withdraw request lifecycle — initiate, cancel, finalize, plus reads for the pending queue.

Reach for **`useWithdraw`** first: it is the **high-level** entry point that takes
just `{ account, amount, receiver }` (amount in the **collateral token's decimals**)
and does the rest — it reads the subaccount's isolation, picks the right withdraw
path, builds the withdraw part, and scales the deallocate amount — so the UI never
branches on where the collateral sits or scales anything. `useInitiateWithdraw` and
the deallocate-and-initiate variant remain available for callers that already know
the isolation and want to drive one specific path, or need custom (multi-part /
cross-chain) withdraw parts.

## Import

```ts
import {
  // Reads
  useExpressWithdrawOptions,
  useExpressWithdrawStatus,
  useExpressWithdrawStatuses,
  useLastWithdrawRequestId,
  usePendingWithdrawRequests,
  useWithdrawRoute,
  useWithdrawRouteChoices,
  useWithdrawRequest,
  useWithdrawableTime,
  // Writes
  useWithdrawWithExpress,
  useWithdraw, // high-level entry point
  useInitiateWithdraw,
  useSimulateInitiateWithdraw,
  useRequestCancelWithdraw,
  useSimulateRequestCancelWithdraw,
  useFinalizeWithdrawRequest,
  useSimulateFinalizeWithdrawRequest,
} from "@symmio/trading-react";
```

## Express-aware withdrawal

Use `useWithdrawRoute` to prepare a route before the user confirms, then pass that exact route to
`useWithdrawWithExpress`. This keeps fee and timing details shown in the UI bound to the signed option submitted on-chain.
The existing `useWithdraw` hook remains the classic-only API.

```tsx
import {
  isExpressWithdrawPayoutComplete,
  useExpressWithdrawStatus,
  useWithdrawRoute,
  useWithdrawWithExpress,
} from "@symmio/trading-react";

function WithdrawPanel({ account, amount, receiver }) {
  const route = useWithdrawRoute({
    user: account,
    amount,
    receiver,
    query: { enabled: amount > 0n },
  });
  const withdraw = useWithdrawWithExpress({ account });
  const requestId = withdraw.data?.requestId;
  const status = useExpressWithdrawStatus({
    user: account,
    requestId: requestId ?? 0n,
    query: { enabled: requestId !== undefined && withdraw.data?.route.kind === "express" },
  });

  const submit = () => {
    if (!route.data) return;
    withdraw.mutate({ amount, receiver, preparedRoute: route.data });
  };

  const paid = status.data ? isExpressWithdrawPayoutComplete(status.data) : false;
  // Render route.data, submit, status.data, and paid.
}
```

### User-selectable Auto, Classic, and Express routes

Use `useWithdrawRouteChoices` when the interface should default to the SDK recommendation but allow an explicit choice.
It performs at most one Express options request for the exact account, amount, and receiver. `recommended` preserves the
existing automatic behavior; `available` contains Classic plus every valid offer returned by the service.

```tsx
const routes = useWithdrawRouteChoices({
  user: account,
  amount,
  receiver,
  query: { enabled: amount > 0n },
});
const automaticWithdraw = useWithdrawWithExpress({ account });
const classicWithdraw = useWithdraw({ account });
// Every route debits the same available balance, so this blocks Classic too.
const overBalance = routes.error?.code === "WITHDRAW_INSUFFICIENT_BALANCE";

function submit(method: "auto" | "classic" | "standard") {
  if (overBalance) return;

  // Classic needs no preview: useWithdraw resolves the account's isolation itself.
  if (method === "classic") {
    classicWithdraw.mutate({ amount, receiver });
    return;
  }

  // Auto and Express submit the exact previewed route.
  if (!routes.data) return;
  if (method === "auto") {
    automaticWithdraw.mutate({ amount, receiver, preparedRoute: routes.data.recommended });
    return;
  }

  const standard = routes.data.available.find(
    (candidate) => candidate.kind === "express" && candidate.option.optionTypeName === "STANDARD",
  );
  if (standard?.kind !== "express") return;
  automaticWithdraw.mutate({ amount, receiver, preparedRoute: standard });
}
```

Reset an explicit selection when the account, amount, receiver, or chain changes. Display only Express choices actually
returned by `available`; if a selected signed offer disappears or expires, disable submission instead of silently using
another route. `useWithdrawRoute` remains the smaller API for automatic-only interfaces.

Classic does not depend on `routes`. Keep it selectable and submittable while the preview loads or fails, and gate only
Auto and Express on `routes.data`. The one exception is `WITHDRAW_INSUFFICIENT_BALANCE`: Classic debits the same
balance, so it would revert too. Route preparation does not retry and does not refetch on window focus or reconnect,
because each attempt may send another recorded `POST /options`. Pair `routes.error` with an explicit retry action that
calls `routes.refetch()`.

The default router first checks that the account's available balance covers the amount, scaled to SYMMIO's 18-decimal
balance units. If it does not, `useWithdrawRoute` and `useWithdrawRouteChoices` (and `useWithdrawWithExpress` without a
`preparedRoute`) fail with `error.kind === "sdk"` and `error.code === "WITHDRAW_INSUFFICIENT_BALANCE"` instead of
returning a route, whatever `policy.fallback` says. Otherwise the router chooses classic immediate withdrawal when the
cooldown is over at the latest block, then prefers `SAME_TX`, then `STANDARD`, and falls back to classic cooldown
withdrawal if the service is disabled or cannot return a usable option. `CUSTOM` accounts retain the classic
deallocate-and-initiate path. Opt into `WINDOWED` or strict service failure explicitly:

```ts
useWithdrawRoute({
  user: account,
  amount,
  receiver,
  policy: {
    optionPriority: ["WINDOWED", "SAME_TX", "STANDARD"],
    fallback: "error",
  },
});
```

<Callout type="warning">
  Express v1 is same-chain only. For a `STANDARD` option, Core `FINALIZED` means the provider recovered its funds—not
  that the receiver was paid. `useExpressWithdrawStatus` keeps polling until provider `PROCESSED`, and
  `isExpressWithdrawPayoutComplete` applies the correct option-aware rule.
</Callout>

### Lower-level hooks

- `useExpressWithdrawOptions` requests signed, non-expired service offers for one exact account, amount, receiver, and
  affiliate. It never retries automatically because `POST /options` creates service records.
- `useExpressWithdrawStatus` polls every three seconds by default. It continues through `NOT_FOUND` while indexing and
  through `STANDARD` + `FINALIZED`; it stops after proven payout or cancellation, suspension, or local failure.
- `useExpressWithdrawStatuses` accepts active on-chain `WithdrawRequest` values and polls the service status of each
  one that belongs to the configured Express provider. Its `entries` only add service status to those requests: classic
  requests and other providers' requests are still active on-chain, so render every request from
  [`usePendingWithdrawRequests`](#usependingwithdrawrequests) and look up an entry for each.
- `useWithdrawRoute` owns safe automatic ordering and classic fallback. Its returned `WithdrawRoute` is the preview
  object accepted by the mutation.
- `useWithdrawRouteChoices` returns the unchanged automatic recommendation plus Classic and all current Express choices
  for interfaces that expose route selection.
- `useWithdrawWithExpress` waits for the mined receipt, decodes the exact `WithdrawInitiated` request id, and returns
  `{ hash, receipt, requestId, route }`. For a classic immediate route it also requires the receipt to finalize that
  same request, and otherwise rejects with `error.code === "WITHDRAW_REQUEST_NOT_FINALIZED"` (see below).

Each hook exports its matching parameter and return aliases:
`UseExpressWithdrawOptionsParameters` / `UseExpressWithdrawOptionsReturnType`,
`UseWithdrawRouteParameters` / `UseWithdrawRouteReturnType`,
`UseWithdrawRouteChoicesParameters` / `UseWithdrawRouteChoicesReturnType`,
`UseExpressWithdrawStatusParameters` / `UseExpressWithdrawStatusReturnType`, and
`UseExpressWithdrawStatusesParameters` / `UseExpressWithdrawStatusesReturnType`,
`UseWithdrawWithExpressParameters` / `UseWithdrawWithExpressReturnType`. The mutation additionally exports
`WithdrawWithExpressVariables` and `WithdrawWithExpressResult`.

After success, `useWithdrawWithExpress` invalidates account balance info, balance-of, withdrawable time, pending requests,
all withdrawal requests, and last request id. It removes every cached Express offer, prepared route, and route-choice list
for that account so a signed offer cannot be accidentally reused. It refreshes the same caches when the transaction mined
but a later receipt check rejected, because the request was still created and its amount debited.

<Callout type="warning">
  **The immediate route can leave a request pending.** It batches `initiateWithdraw` and `finalizeWithdrawRequest` into
  one transaction and has to guess the new request's id. If another request for the same subaccount lands first (a
  second tab, a session key), the batch either reverts or finalizes that other request, leaving the new one pending with
  its amount debited. The hook then rejects with `{ kind: "sdk", code: "WITHDRAW_REQUEST_NOT_FINALIZED" }` instead of
  reporting success. The refreshed [`usePendingWithdrawRequests`](#usependingwithdrawrequests) list shows the request;
  offer [`useFinalizeWithdrawRequest`](#usefinalizewithdrawrequest--usesimulatefinalizewithdrawrequest) or
  [`useRequestCancelWithdraw`](#userequestcancelwithdraw--usesimulaterequestcancelwithdraw) for it.
</Callout>

## `useWithdraw` — high-level withdraw

Pass the subaccount `account` to the hook, then `mutate` with a **minimal input**:
`{ amount, receiver }`, with `amount` in the **collateral token's decimals** (e.g. 6
for USDC). You do not pass `isolationType`, build `parts`, or scale anything — the
hook reads the subaccount's `SubAccountIsolationType` via `useSubAccount` (deduped by
react-query with any other `useSubAccount` on the same key, e.g. one driving a balance
display), builds the classic same-chain withdraw part,
scales the deallocate amount, and dispatches on the isolation, which determines
**which balance the funds are in** and therefore which underlying action runs:

| `isolationType`                    | Where the funds sit | What runs                                                                      |
| ---------------------------------- | ------------------- | ------------------------------------------------------------------------------ |
| `CUSTOM` (cross-margin)            | allocated (margin)  | `deallocateAndInitiateWithdraw` — deallocate **and** initiate in one atomic tx |
| `MARKET` / `MARKET_DIRECTION` (VA) | available           | `initiateWithdraw` — initiate only                                             |

A `CUSTOM` subaccount holds its collateral in the **allocated** balance, so it must
first be deallocated into the available balance; that path batches both legs into a
single transaction. Account-layer balances are `1e18`-scaled regardless of the
collateral token's decimals, so the hook scales your collateral-decimals `amount` to
the 18-decimal amount the deallocate leg needs. The VA modes already hold their funds
in the **available** balance, so they only initiate the request.

```tsx
import { useWithdraw } from "@symmio/trading-react";

const { mutate } = useWithdraw({ account });

// amount in the collateral token's decimals (6-dec USDC → 1 USDC):
mutate({ amount: 1_000000n, receiver });
```

On success it invalidates the subaccount's balance reads (`balanceInfo`, `balanceOf`), pending and complete withdrawal
reads, last request id, and withdrawable time. It also removes cached Express offers and route preparations because the
submitted Classic request makes those signed choices stale. On the `CUSTOM` path the SDK fetches a fresh Muon uPnL
signature for the deallocate leg unless you
pass one as `upnlSig`. Backed by the core [`withdrawAuto`](../symmio-contract#withdrawauto--high-level-entry-point)
action; reach for `useInitiateWithdraw` / the deallocate-and-initiate variant when
you already know the isolation or need custom withdraw parts.

## Lifecycle overview

1. **Initiate** — `useInitiateWithdraw` submits a withdraw request. Enters the delayed queue.
2. **Wait** — `useWithdrawableTime` tells the UI when the request becomes claimable.
3. **Finalize** — `useFinalizeWithdrawRequest` claims the funds after the delay.
4. **Cancel** (optional) — `useRequestCancelWithdraw` cancels a pending request.

Each write has a paired `useSimulate*` — see [Simulate then write](../concepts/simulate-then-write).

## Reads

### `useLastWithdrawRequestId`

Id of the most recent request for an account.

```ts
const lastId = useLastWithdrawRequestId({ account });
```

### `usePendingWithdrawRequests`

A subaccount's active (non-terminal) withdraw requests, classic and provider-backed alike, from the id range the core
[`getPendingWithdrawRequests`](/core/symmio-contract/get-pending-withdraw-requests) scans (`start` / `size`, ids 1–200
by default).

```ts
const pending = usePendingWithdrawRequests({ user: subAccount });
```

Render **every** request it returns. Pair it with `useExpressWithdrawStatuses` to add service progress to the requests
of the configured Express provider, which also recovers that progress after remounting or refreshing the page. Its
`entries` only add status: classic requests and other providers' requests have no entry but are still active on-chain,
so dropping them would hide a debited balance. Gate each row's buttons with `getWithdrawRequestActions`, and an Express
row's Cancel also with `isExpressWithdrawCancellable`:

```tsx
import {
  getWithdrawRequestActions,
  isExpressWithdrawCancellable,
  isExpressWithdrawPayoutComplete,
  useExpressWithdrawStatuses,
  usePendingWithdrawRequests,
} from "@symmio/trading-react";

const pending = usePendingWithdrawRequests({ user: subAccount });
const express = useExpressWithdrawStatuses({
  requests: pending.data ?? [],
  enabled: pending.data !== undefined,
});
const entries = new Map(express.entries.map((entry) => [entry.request.id, entry]));

for (const request of pending.data ?? []) {
  const entry = entries.get(request.id);
  // The receiver is already paid, so nothing is left to do.
  if (entry?.status && isExpressWithdrawPayoutComplete(entry.status)) continue;

  const actions = getWithdrawRequestActions(request);
  if (!entry) {
    // Classic or another provider: offer Finalize (from request.cooldownEndTime on) and Cancel per `actions`.
  } else {
    // Configured Express provider: show entry.status and no Finalize; the service drives payout.
    const canCancel =
      actions.cancel && (entry.status ? isExpressWithdrawCancellable(entry.status) : entry.error !== null);
  }
}
```

Show `pending.error` before an empty state, so a failed read never reads as "no withdrawals". An Express entry with
neither `status` nor `error` is still loading its first status, so hold its Cancel until that read settles. When the
service is unreachable (`entry.error`), Core's cancel is still valid and the write simulates first by default.

`useExpressWithdrawStatuses` polls each entry with the same payout-aware policy as `useExpressWithdrawStatus`. A
`STANDARD` request leaves the pending list once Core finalizes it (provider `FINALIZED`), which can be before the
provider pays the receiver; to show that last step, keep polling it by id with `useExpressWithdrawStatus` until provider
`PROCESSED`.

### `useWithdrawRequest`

Details for one specific request.

```ts
const request = useWithdrawRequest({ account, requestId });
```

### `useWithdrawableTime`

Timestamp when a queued request becomes claimable. Bind to a countdown / claim button.

```ts
const { withdrawableAt, isReady } = useWithdrawableTime({ requestId });
```

## Writes

<Callout type="info">
  Every write on this page is [relayable](/core/gasless/relayable-writes): pass `gasless: true` in the mutation
  variables to sign it as an InstantLayer operation and let the relayer pay the gas. See [Gasless
  hooks](/react/gasless). A relayed write still pays an operational fee from the Core balance — budget it first, as
  [Gasless withdrawals](#gasless-withdrawals) describes.
</Callout>

### `useInitiateWithdraw` / `useSimulateInitiateWithdraw`

Submit a withdraw request directly, without the isolation dispatch. This is the
**initiate-only** leg — the right call for a `MARKET` / `MARKET_DIRECTION` (VA)
subaccount whose funds are already in the available balance, or when you drive the
`deallocateAndInitiateWithdraw` variant yourself for a `CUSTOM` subaccount. Prefer
[`useWithdraw`](#usewithdraw--high-level-withdraw) when you don't want to
branch on isolation.

```ts
const simulation = useSimulateInitiateWithdraw({ account, amount });
const mutation = useInitiateWithdraw();
```

### `useRequestCancelWithdraw` / `useSimulateRequestCancelWithdraw`

Cancel a pending request. The call routes through the AccountLayer `_call` proxy, so the connected wallet must own the
subaccount. Offer it only when [`getWithdrawRequestActions(request).cancel`](/core/symmio-contract/get-withdraw-request-actions)
is `true`, and for a configured Express request only while `isExpressWithdrawCancellable(status)` is too.

```ts
const mutation = useRequestCancelWithdraw();
mutation.mutate({ account, requestId });
```

### `useFinalizeWithdrawRequest` / `useSimulateFinalizeWithdrawRequest`

Claim funds after the delay expires. The call is permissionless and keyed by the request's owner as `user`. Offer it only
when [`getWithdrawRequestActions(request).finalize`](/core/symmio-contract/get-withdraw-request-actions) is `true`, keep
it disabled until the request's `cooldownEndTime`, and leave it off configured Express requests, where it would pay the
provider rather than the receiver.

```ts
const mutation = useFinalizeWithdrawRequest();
mutation.mutate({ user: account, requestId });
```

## Gasless withdrawals

Relaying a withdrawal removes the gas, not the cost. The GaslessLayer charges an operational fee **after** the operation executes, from the Core balance of the account that pays — for a plain withdrawal, the sub-account itself. The withdrawal and its fee draw on the same balance, so budget both, in Core units:

```text
required Core balance = withdrawal amount in Core units + operational fee in Core units
```

The withdrawal `amount` is in the collateral token's decimals, while the Core balance and the fee are 18-decimal. Convert the amount with [`collateralToCore18`](/core/shared-types#collateraltocore18) before you compare. A `MARKET` / `MARKET_DIRECTION` sub-account withdraws from its available balance:

```tsx
import { collateralToCore18 } from "@symmio/trading-core";
import { useAccountBalanceOf, useSymmioChainId, useSymmioConfig, useWithdraw } from "@symmio/trading-react";

const config = useSymmioConfig();
const chainId = useSymmioChainId();
const { collateralDecimals } = config.getChainConfig(chainId).addresses;
const balance18 = useAccountBalanceOf({ account }).data; // 18-decimal Core units

const required18 = collateralToCore18(amount, collateralDecimals) + fee18;
const affordable = balance18 !== undefined && balance18 >= required18;

const { mutate } = useWithdraw({ account });
mutate({ amount, receiver, gasless: true }); // amount stays in collateral decimals
```

A `CUSTOM` sub-account holds its funds in the allocated balance and deallocates the amount first, so budget the same total against its `allocatedBalance` from [`useAccountBalanceInfo`](/react/account-layer#useaccountbalanceinfo). The fee is drawn from the free balance first, then from the allocated balance.

`fee18` is the operation's quoted fee — `totalFee18` from [`useGaslessFeeQuote`](/react/gasless#usegaslessfeequote) for the batch you relay. The quote is a preview, so keep a margin, and reserve the budgets of any other relayed operations still pending. Neither the quote nor the transparent mode's fee pre-flight checks that the payer can afford the fee. A shortfall is refused before acceptance with `SIMULATION_REVERTED` and the Core revert `OperationalFee: Insufficient balance`, which approving more allowance does not fix. Read current fees rather than hard-coding them; they are deployment configuration.

<Callout type="warning">
  **A relayed withdrawal that succeeds is _initiated_, not received.** A `succeeded` relay, and the mutation that
  resolves with it, means the withdraw request exists on-chain and its amount has left the Core balance. The funds reach
  the receiver only after the cooldown and a separate finalize. Show "withdrawal initiated" until then, and follow the
  request with `useWithdrawableTime` and `usePendingWithdrawRequests`.
</Callout>

**Finalizing and cancelling cost a fee too when relayed.** Each is its own relayed operation, charged in Core units to the request's sub-account unless the daily free quota covers it:

- A relayed **finalize** adds nothing to the Core balance, so the fee must still be there when it runs. Withdrawing the whole balance leaves nothing to pay it with. Keep the fee back, or finalize from the wallet (`gasless: false`), which costs native gas but no operational fee.
- A relayed **cancel** of a pending request refunds the amount before the fee is collected, so the refund can cover the fee. A cancel that only asks the request's withdraw provider to cancel refunds nothing yet, so it needs the reserve as well.
