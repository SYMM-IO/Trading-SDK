# resolveListingService

Resolve the Pools **listing backend** for a `{ chainId, solverId }` target. Every Pools read runs this first, so a target without Pools fails with a typed error instead of a request to a backend that is not there.

```ts
import { resolveListingService } from "@symmio/trading-core";

const { url } = resolveListingService(config, { chainId });
```

Availability has two halves, and this function requires **both**:

1. the resolved solver declares the `listingService` capability, and
2. the resolved chain carries a `listing` block.

The capability lives on the solver because it is the solver's markets that are listed; the URL lives on the chain because several solvers on one chain could share one listing deployment. Today only **enigma on HyperEVM** satisfies both.

## Parameters

<Properties>
  <Property name="chainId" type="number" optional>
    Target chain id. Defaults to the config's `defaultChainId`.
  </Property>
  <Property name="solverId" type="SolverId" optional>
    Solver to check. Defaults to the chain's `defaultSolverId`.
  </Property>
</Properties>

Both functions take the same object, exported as `ResolveListingServiceParameters`.

## Returns

<Returns type="SymmioListingConfig">
  <Property name="url" type="string">
    Listing backend **host root** — no version segment and no trailing slash, e.g. `https://listing85.enigma.bz`.
  </Property>
</Returns>

<Callout type="warning">
  The `url` is a host root on purpose. The generated client's own paths already begin with `/v2`, so a versioned base
  URL would request `/v2/v2/market/search` and 404. Point it at staging (`https://listing-staging.enigma.bz`) with a
  `createConfig` override — there is no separate environment axis.
</Callout>

## Throws

Both are a `SymmError` with `kind: "config"`, raised before any network call:

- `LISTING_UNSUPPORTED` — the resolved solver does not use the listing service. The message names the solver, e.g. `Pools: solver "Rasa" (kind "rasa") does not use the listing service.`
- `LISTING_NOT_CONFIGURED` — the solver uses the service, but the chain has no `listing` backend configured.

The capability is checked first, so a solver that does not do Pools reports `LISTING_UNSUPPORTED` even on a chain that has a backend configured for some other solver.

## supportsListingService

The non-throwing twin. Same parameters, returns a boolean.

```ts
import { supportsListingService } from "@symmio/trading-core";

if (supportsListingService(config, { chainId })) showPoolsTab();
```

It swallows every failure `resolveListingService` can raise — a solver without the capability, a chain without a backend, **and** an unknown chain or solver id — and returns `false`. That last case matters: it means you can call it with a chain id straight off a wallet, before knowing whether the SDK supports that chain at all.

## Which to use

| Situation                                                                  | Reach for                |
| -------------------------------------------------------------------------- | ------------------------ |
| Inside an action or server handler that cannot proceed without the backend | `resolveListingService`  |
| Deciding whether to render a Pools tab, route, or column                   | `supportsListingService` |
| An `enabled` flag on a query or hook                                       | `supportsListingService` |
| You need the `url` itself                                                  | `resolveListingService`  |

The rule of thumb: throw where absence is a bug, and return `false` where absence is just a chain that does not have this product. Using `resolveListingService` inside a `try` to produce a boolean is `supportsListingService` written out longhand.

```ts
const enabled = supportsListingService(config, { chainId });

const { data } = useQuery({
  ...getListingMarketsQueryOptions(config, { chainId }),
  enabled,
});
```
