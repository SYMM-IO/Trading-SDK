# listMarket

List a token as a pool — or **relist** a delisted one — with the permissionless listing service. `listMarket` submits the token and its pool economics to `POST /v2/market/list-market`, which handles both cases through one flow, and returns the accepted [`CreatedPool`](#returns) with the custodial deposit wallet to seed the pool.

```ts
import { listMarket, ListingDepositChainId } from "@symmio/trading-core";

const pool = await listMarket(config, {
  accessToken: token.accessToken,
  tokenContractAddress: "0xToken…",
  buyBackRatio: 5,
  maxLeverage: 20,
  depositChain: ListingDepositChainId.BASE,
});
// send the listing deposit to `pool.walletPublicKey` to seed the pool
```

The pool starts at [`ListingMarketStatus.WAITING_FOR_DEPOSIT`](/core/pools/listing-market-type) and stays there until the listing deposit lands at `walletPublicKey`. This is the authenticated write twin of the Pools reads — it takes the same Bearer `accessToken` as [`getUserListingMarkets`](/core/pools/get-user-listing-markets).

<Callout type="info">
  **Upgrading from `addMarket`?** `addMarket`, `addMarketMutationOptions` and `useAddMarket` are removed. Call
  `listMarket` / `listMarketMutationOptions` / [`useListMarket`](/react/pools#uselistmarket) with the same parameters:
  the request body and the `CreatedPool` result are unchanged. Rename `AddMarketParameters` to `ListMarketParameters`,
  `toAddMarketRequest` to `toListMarketRequest`, and check for `LIST_MARKET_FAILED` instead of `ADD_MARKET_FAILED`.
</Callout>

## New listing or relist

The service decides from the token's current market, not from a parameter:

| The token's market                    | What `listMarket` does                                                                                                                                                                                   |
| ------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| None                                  | Opens a new listing: resolves the token's name / ticker / decimals from the contract, provisions a deposit wallet, and returns the pool at [`WAITING_FOR_DEPOSIT`](/core/pools/listing-market-type).     |
| `DELISTED`                            | Relists it through the same flow and returns the pool at `WAITING_FOR_DEPOSIT` with the deposit wallet to fund again. The original listing time is kept; the service records the relist time separately. |
| Any other status (`LISTED`, pending…) | Rejected by the service — surfaces as `LIST_MARKET_FAILED` (see [Throws](#throws)).                                                                                                                      |

Relisting works **only from `DELISTED`**. A relist whose token validation fails is rejected and leaves the market delisted — there is no partial state to clean up.

<Callout type="info">
  Two other Pools reads feed this write. The recommended initial deposit and the set of deposit chains a listing form
  should offer come from [`getListingConfig`](/core/pools/listing-config) — derive the `depositChain` picker from its
  `supportedDepositChains` rather than hardcoding a list. And listing is capped protocol-wide per week (a relist uses a
  slot too): read [`getWeeklyListingLimit`](/core/pools/weekly-limit) (a public read) first and **block** `listMarket`
  when `remaining` is `0` (the service's own weekly-limit rejection otherwise surfaces here as a `LIST_MARKET_FAILED`
  after a round-trip).
</Callout>

<Callout type="info">
  This is a REST write against the listing backend, not a contract call, and it is **authed**: the `accessToken` from
  [`authenticateListing`](/core/pools/listing-auth) is sent as an `Authorization: Bearer <token>` header. The backend is
  resolved from the config before the request, so a target without Pools fails immediately and without any network
  traffic — see [`resolveListingService`](/core/pools/resolve-listing-service).
</Callout>

## Token metadata for your UI

`listMarket` needs only the token's **contract address** — the listing backend resolves the name, ticker, and decimals from the chain itself and returns them on [`CreatedPool`](#returns). A listing form, though, usually wants to **show** the token _before_ the user submits: its name, symbol, price, market cap, and liquidity.

That preview data is not part of this SDK. When you need it, fetch it from **DexScreener** by token address:

```http
GET https://api.dexscreener.com/latest/dex/tokens/<token_address>
```

Use the response to display and sanity-check the token — confirm it exists, show its name / logo, and check its liquidity — in your listing UI before calling `listMarket`.

## The access token

`accessToken` is required — the endpoint is authed and rejects an unauthenticated request. Mint it once with [`authenticateListing`](/core/pools/listing-auth) (the SIWE exchange), hold it, and pass it on the call. A bad or expired token comes back as a `401` (see [Throws](#throws)) — refresh it and retry.

## Pre-submit reads

Before submitting, read [token validation](/core/pools/token-validation), [listing config](/core/pools/listing-config), and the [weekly limit](/core/pools/weekly-limit), and read [`getListingMarketDetail`](/core/pools/market-detail) to tell a new listing from a relist or an existing market. Keep the deployment `chainId` separate from the token's `depositChain`. Sending the listing deposit is the app's job: the SDK returns the deposit wallet but does not move funds.

## Parameters

`accessToken`, `tokenContractAddress`, `buyBackRatio`, `maxLeverage`, and `depositChain` are required. Every other field is an optional listing extra — the SDK leaves it **absent from the request unless you set it**, so an integrating app supplies its own defaults rather than the SDK inventing them.

<Properties>
  <Property name="accessToken" type="string" required>
    Bearer token from [`authenticateListing`](/core/pools/listing-auth). Sent as `Authorization: Bearer <token>`. A bad
    or expired token yields a `401`.
  </Property>
  <Property name="tokenContractAddress" type="string" required>
    The token to list or relist, as an EVM (`0x…`) or Solana (base58) contract address. Typed as `string`, not viem's
    `Address`, because a Solana listing carries a non-`0x` base58 address.
  </Property>
  <Property name="buyBackRatio" type="number" required>
    Share of trading fees routed to buy-backs, `0`–`100`.
  </Property>
  <Property name="maxLeverage" type="number" required>
    Maximum leverage the market allows, as a whole multiplier (`20` = 20x), `1`–`100`.
  </Property>
  <Property name="depositChain" type="ListingDepositChainId" required>
    Chain the token lives on and where its listing deposit will be made — e.g. `ListingDepositChainId.BASE`. A market
    is identified by its token **and** deposit chain.
  </Property>
  <Property name="isTax" type="boolean" optional>
    Whether the token charges a transfer tax. Sent only when set.
  </Property>
  <Property name="userWhitelistTax" type="boolean" optional>
    Whether the deposit wallet is whitelisted from the token's transfer tax. Sent only when set.
  </Property>
  <Property name="additionalChains" type="readonly number[]" optional>
    Extra chain ids the token can also be deposited on. Sent only when set — an empty array **is** sent, as an empty
    list.
  </Property>
  <Property name="poolAddress" type="string" optional>
    An existing pool address to attach, when the token already has one. Sent only when set.
  </Property>
  <Property name="cexList" type="readonly string[]" optional>
    CEX names the token trades on, e.g. `"Binance"`. Sent only when set.
  </Property>
  <Property name="chainId" type="number" optional>
    Target chain id. Defaults to the config's `defaultChainId`. Selects which chain's listing backend is used.
  </Property>
</Properties>

<Callout type="warning">
  The optional extras are **absent unless set** — the SDK does not default them. `isTax` / `userWhitelistTax` are simply
  omitted when unset; `additionalChains` / `cexList` are omitted when unset and sent as an empty list when set to `[]`.
  An integrating app (e.g. `apps/web`) decides its own defaults and passes them explicitly.
</Callout>

## Returns

  <Property name="tokenDecimal" type="number">
    The token's on-chain decimals the service read from the contract.
  </Property>
  <Property name="buyBackRatio" type="number">
    Share of trading fees routed to buy-backs, `0`–`100`, as submitted.
  </Property>
  <Property name="maxLeverage" type="number">
    Maximum leverage the market will allow, as a whole multiplier, as submitted.
  </Property>
  <Property name="depositChain" type="ListingDepositChainId">
    Chain the token lives on and where its listing deposit must be made.
  </Property>
  <Property name="marketStatus" type="ListingMarketStatus">
    Where the market sits in the listing lifecycle — a new listing and a relist both start at `WAITING_FOR_DEPOSIT`.
  </Property>
  <Property name="walletPublicKey" type="string | null">
    The custodial deposit wallet to **seed the pool** — send the listing deposit here. `null` when the service did not
    return one; resolve it with [`getDepositAddress`](/core/pools/deposit-address) before sending funds.
  </Property>
  <Property name="mainPool" type="string | null">
    The main pool address, or `null` when the service has not assigned one yet.
  </Property>
  <Property name="isTax" type="boolean | null" optional>
    The token's transfer-tax flag as the service echoed it; `null` when it did not report one.
  </Property>
  <Property name="userWhitelistTax" type="boolean | null" optional>
    Whether the deposit wallet is whitelisted from the token's tax; `null` when not reported.
  </Property>
  <Property name="additionalChains" type="number[] | null" optional>
    The other deposit chain ids the service recorded; `null` when not reported.
  </Property>
  <Property name="cexList" type="string[] | null" optional>
    The CEX names the service recorded; `null` when not reported.
  </Property>
</Returns>

<Callout type="info">
  Money and config fields on `CreatedPool` are plain `number`s as the service reports them — **not** the 18-decimal
  `bigint` scale of the catalog rows ([`ListingMarket`](/core/pools/listing-market-type)). `listMarket` returns the
  accepted application, not live pool metrics, so there is nothing to descale here.
</Callout>

## Mutation options

```ts
import { listMarketMutationOptions } from "@symmio/trading-core";
import { useMutation } from "@tanstack/react-query";

const { mutateAsync } = useMutation(listMarketMutationOptions(config));
const pool = await mutateAsync({
  accessToken,
  tokenContractAddress: "0xToken…",
  buyBackRatio: 5,
  maxLeverage: 20,
  depositChain: ListingDepositChainId.BASE,
});
```

`listMarket` is modeled as a **mutation**, not a query: it submits a listing (or relisting) application that provisions a deposit wallet, so it is a one-shot write rather than cached data. `listMarketMutationOptions(config)` returns the `{ mutationKey: ["listMarket"], mutationFn }` bag to hand to `useMutation`. The mapping helpers `toListMarketRequest` (parameters → wire request) and `toCreatedPool` (response → `CreatedPool`) are exported too, for callers driving the request themselves.

## Throws

- `LISTING_NOT_CONFIGURED` — a `SymmError` (`kind: "config"`) when the chain has no `listing` backend configured. Gate with `supportsListingService` to hide the listing flow instead of erroring. No request is sent.
- `LIST_MARKET_FAILED` — the request itself failed. Any axios failure becomes a `SymmApiError` carrying `status`, `statusText`, `responseData`, `url` and `method` — `status` is `0` when no response came back; a non-axios throw becomes a plain `SymmError` (`kind: "api"`) with the original error as its `cause`. The service's rejections all surface here with its own status and body in `responseData`:
  - a **`401`** — the `accessToken` was missing, malformed, or expired; re-run `authenticateListing` and retry;
  - a market for this token and deposit chain **already exists and is not delisted**;
  - the token failed validation (including during a relist, which leaves the market delisted);
  - the weekly listing limit is reached.

<Callout type="warning">
  The SDK does not yet map the service's rejection reasons to typed errors — branch on `status` and the service's
  `responseData` until it does.
</Callout>
