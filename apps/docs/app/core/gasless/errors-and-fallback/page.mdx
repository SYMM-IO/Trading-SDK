# Errors & fallback

How gasless failures surface, how to read the vendor's diagnostics out of them, when a wallet-paid retry is safe, and what to do when a submit's outcome is simply unknown.

## The fallback safety rule

<Callout type="warning">
  A wallet-paid retry of the same intent is safe **only** when the relay definitively refused it *before any broadcast*:
  a fee/quota rejection, or the gateway dropping the request before any service saw it (`429`, or a `503` carrying the
  gateway's own envelope). Never on a timeout, a `502`/`504`, a status `0`, an idempotency conflict, or anything after a
  `202` — the relayed transaction may still execute, and a wallet duplicate would execute the same intent twice.
</Callout>

Two predicates encode exactly this — use them instead of re-deriving the rule:

```ts
import { isConfirmedGaslessFeeLimitError, isConfirmedGaslessUnavailableError } from "@symmio/trading-core";

try {
  await relayInstantOperations(config, parameters);
} catch (err) {
  const safeToUseWallet =
    isConfirmedGaslessFeeLimitError(err) || (!accepted && isConfirmedGaslessUnavailableError(err));
  if (!safeToUseWallet) throw err;
  // …fall back to the gas-paid path
}
```

Both work on the error a React hook throws too: `SymmioRequestError` keeps the status and the response body, and every gasless predicate reads them structurally rather than through an `instanceof` check.

The [transparent execution mode](/core/gasless/relayable-writes) applies them for you under `fallback: "wallet"`, with the same exclusions hard-coded: an unconfirmed submit, an idempotency conflict and a `2xx` from the wrong protocol instance end the write, whatever `fallback` says.

One more rejection is safe to retry through the wallet, because it happens before anything is signed: the fee pre-flight finding the daily free quota exhausted (`GASLESS_FREE_QUOTA_EXHAUSTED`, matched by `isGaslessFreeQuotaExhaustedError`). The transparent mode falls back on it too. A fee quote that fails for transport reasons is not a rejection: the transparent mode signs and relays anyway, and the relayer's simulation decides.

### The matrix

| Outcome                                                                                                                | SDK behavior                                             | Wallet fallback    |
| ---------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------- | ------------------ |
| `429`, or `503` with the gateway `{ error }` envelope                                                                  | Resent under the same key, up to twice, then thrown      | **Yes**            |
| Fee code (`FEE_POLICY_WOULD_REVERT` / `INSUFFICIENT_ALLOWANCE`) on any `4xx`                                           | Thrown as-is                                             | **Yes**            |
| `400 SIMULATION_REVERTED` with a billing revert (`OperationalFee: …`, `DailyFreeOpsLimitExceeded`, `FeeLimitExceeded`) | Thrown as-is                                             | **Yes**            |
| A stored record that ended `rejected` for a billing reason                                                             | Thrown by the dispatcher / `confirmGaslessRequest`       | **Yes**            |
| Status `0`, a timeout, `500`, `502`, `504`, `503` without the envelope                                                 | Resent once, then `GASLESS_SUBMIT_UNCONFIRMED`           | **No** — resubmit  |
| A `2xx` with no `request_id`                                                                                           | `GASLESS_SUBMIT_UNCONFIRMED`                             | **No** — resubmit  |
| A `2xx` from another protocol instance                                                                                 | `GASLESS_INSTANCE_MISMATCH`, body kept in `responseData` | **No** — reconcile |
| `409 IDEMPOTENCY_KEY_CONFLICT`                                                                                         | Thrown as-is                                             | **No** — new key   |
| `404` with the gateway envelope                                                                                        | Thrown as-is                                             | **No** — config    |
| `401` / `403` / `422`, any other `4xx`                                                                                 | Thrown as-is                                             | **No**             |
| Anything after a `202` that is not a billing `rejected`                                                                | `GASLESS_RELAY_REJECTED` / `_FAILED` / `_REVERTED`       | **No**             |

`502` and `504` look like outages and are not treated as one on purpose. The gateway returns `502` for an upstream failure **and** for a protocol-instance identity mismatch, and either can happen after the body reached the service — which is exactly the shape that produced a double execution when the SDK treated them as "definitely not accepted".

## When the outcome is unknown

A submit that fails ambiguously is resent **once** by the SDK under the same idempotency key. If that is inconclusive too, it throws `GASLESS_SUBMIT_UNCONFIRMED` carrying the exact bytes that were sent:

```ts
import { getGaslessUnconfirmedSubmit, resubmitGaslessRequest } from "@symmio/trading-core";

const pending = getGaslessUnconfirmedSubmit(err);
if (pending) {
  await store.save(pending); // { chainId, service, path, body, idempotencyKey }
  await resubmitGaslessRequest(config, pending);
}
```

Resending the identical request under the same key either lands it or returns the record the service already created, so it can never double-execute. See [`resubmitGaslessRequest`](/core/gasless/resubmit-gasless-request) — and keep the record out of third-party logging, because `body` holds the user's signed operations.

### Idempotency keys

One key describes **one payload**. Reuse it only to replay the byte-identical request; change anything — re-sign, add an operation, move a wallet id, settle again after a terminal status — and the key must change too, or the service answers `409 IDEMPOTENCY_KEY_CONFLICT` (`isGaslessIdempotencyConflictError`).

That is why only the actions whose payload **you** build take an `idempotencyKey`:

| Action                                                                                         | `idempotencyKey`                                       |
| ---------------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| [`relayInstantOperations`](/core/gasless/relay-instant-operations)                             | Yours — you signed the operations                      |
| [`settleGaslessDepositNewAccount`](/core/gasless/settle-gasless-deposit-new-account)           | Yours — the payload is data, not a signature           |
| [`settleGaslessDepositExistingAccount`](/core/gasless/settle-gasless-deposit-existing-account) | Yours                                                  |
| [`gaslessWalletExecute`](/core/gasless/gasless-wallet-execute)                                 | Minted per call — it signs a fresh operation each time |
| [`relayGrantDelegation`](/core/gasless/relay-grant-delegation)                                 | Minted per call                                        |
| [Transparent writes](/core/gasless/relayable-writes) (`gasless: true`)                         | Minted per call                                        |

Every acceptance receipt echoes the key that was used, so a relay you did not key yourself is still reconcilable — persist `requestId`, `owner`, `walletIds` and `idempotencyKey` together.

## Reading the vendor detail

HTTP failures are thrown as `SymmApiError` with the raw response body preserved; `parseGaslessErrorDetail` digs the vendor's `{ code, message, details }` envelope out of any gasless error — including whatever the service decoded of an on-chain revert:

```ts
import { parseGaslessErrorDetail } from "@symmio/trading-core";

const detail = parseGaslessErrorDetail(err);
detail?.code; // "SIMULATION_REVERTED", "INSUFFICIENT_ALLOWANCE", …
detail?.contractRevert?.error; // "InvalidWalletOperationTarget", …
detail?.revertMessage; // "OperationalFee: Insufficient balance"
detail?.decodedRevert; // the service's own decoded view, in whatever shape it sent
detail?.rpcError; // the nested JSON-RPC error, when the failure came from the chain
detail?.failedOperation; // { index, revertData } of an OperationFailed revert
detail?.gatewayError; // "Unknown or disabled protocol instance: …" (the gateway's own { error } body)
detail?.validationErrors; // [{ loc: ["path", "request_id"], msg, type }] (a 422)
```

`revertMessage`, `decodedRevert`, `rpcError` and `failedOperation` are read from both `detail` and `detail.details`, because deployments differ on which level they use.

`contractRevert.arguments` is `readonly unknown[] | Record<string, unknown>`: the vendor sends a positional array or an object keyed by parameter name depending on how it decoded the revert. Narrow with `Array.isArray` before indexing, or read `contractRevert.decoded`, which is a plain string on the deployments that key their arguments.

### Naming the failing batch entry

A relayed batch is atomic, so the InstantLayer reports an inner failure as `OperationFailed(operationIndex, revertData)` — a position, not a cause. Decode it against the ABI the failing operation targeted:

```ts
import { accountLayerAbi, decodeGaslessOperationFailure } from "@symmio/trading-core";

const failure = decodeGaslessOperationFailure(err, accountLayerAbi);
failure?.index; // 1
failure?.decoded?.errorName; // "InvalidNameLength"
```

### Classifying a failure

`classifyGaslessFailure` reduces any gasless failure to the one reason a UI should act on, reading the decoded revert ahead of the vendor code and the vendor code ahead of the HTTP status — a `400 SIMULATION_REVERTED` whose revert names an allowance shortfall is an allowance problem, not a bad request:

```ts
import { classifyGaslessFailure } from "@symmio/trading-core";

switch (classifyGaslessFailure(err)) {
  case "payer-balance":
    return showTopUp(); // an allowance approval will not fix this
  case "fee-allowance":
    return showApproveOperationalFee();
  case "submit-unconfirmed":
    return showReconcilePending(getGaslessUnconfirmedSubmit(err));
  default:
    return showDiagnostics(parseGaslessErrorDetail(err));
}
```

| Reason                                                                                               | What the user can do                                                                   |
| ---------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| `"payer-balance"`                                                                                    | Top up the billing account's SYMMIO collateral. Approving more allowance does nothing. |
| `"fee-allowance"`                                                                                    | Approve more with [`approveOperationalFee`](/core/gasless/approve-operational-fee).    |
| `"free-quota"`                                                                                       | Wait for the UTC reset, or pay from the wallet.                                        |
| `"fee-limit"`                                                                                        | The fee policy refused it; refresh the policy before rebuilding.                       |
| `"failed-operation"`                                                                                 | Decode the entry with `decodeGaslessOperationFailure` and fix that call.               |
| `"nonce-or-deadline"`                                                                                | Refresh the nonce and deadline and ask for a new signature.                            |
| `"deposit-below-minimum"` / `"deposit-not-above-fees"`                                               | Fund the deposit address further, or wait for finality.                                |
| `"idempotency-conflict"`                                                                             | Mint a new key; reconcile the workflow the old one created.                            |
| `"client-schema"`                                                                                    | A client bug — fix the payload, do not retry.                                          |
| `"rate-limited"` / `"unauthorized"` / `"forbidden"` / `"unknown-instance"` / `"gateway-unavailable"` | Gateway-level; see the status table below.                                             |
| `"submit-unconfirmed"`                                                                               | Resubmit. Never re-run the intent.                                                     |
| `"simulation-reverted"`                                                                              | Rebuild, re-sign, new key. Never resend the same signature.                            |
| `"unknown"`                                                                                          | Show the raw diagnostics.                                                              |

### Diagnostics for a support report

Capture the environment, protocol instance, service, idempotency key, request id and transaction hash if they exist, the HTTP status and vendor code, and the decoded revert — **without credentials**.

The error never carries credentials by construction: a gasless HTTP failure keeps no request headers and no request body. Its `cause` is a sanitized snapshot of the failure (`name`, `message`, `code`, `status`, `method`, `url`), and the URL drops any userinfo and query string.

`responseData` is a different matter. A FastAPI `422` echoes the rejected input in each `detail[].input` and `ctx` — for a missing field that is the whole parent object, which can include the signed operations and their signatures, and a signature the service rejected was never executed, so it stays valid until its deadline. `GASLESS_SUBMIT_UNCONFIRMED`'s `responseData` deliberately holds the signed body too. Before sending a gasless error to third-party logging, drop or redact `responseData`; log a `422` through `parseGaslessErrorDetail(err)?.validationErrors`, which keeps only `loc`, `msg` and `type`.

## Gateway statuses

The gateway answers some failures itself, before any service sees the request, with a `{ "error": "…" }` body instead of the service's `{ "detail": … }` envelope; `parseGaslessErrorDetail(err)?.gatewayError` holds that string. Every HTTP failure is a `SymmApiError` with its `status`:

| Status                    | Meaning                                                                                                                                                                        | What to do                                                                                                                                                               |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `0`                       | No response: a network failure, or a submit that ran past `execution.submitTimeoutMs`. In a browser, also a CORS rejection of the app's Origin.                                | Ambiguous for a submit: resend the same bytes under the same key. A CORS rejection persists until the gateway allows the Origin.                                         |
| `400` with `gatewayError` | The URL and a protocol-instance selector disagree, or the selector is invalid.                                                                                                 | Fix the `url` / `protocolInstance` pairing.                                                                                                                              |
| `401`                     | Invalid, disabled, conflicting or malformed credentials, or no key at all where the deployment has turned anonymous access off (`gatewayError` then starts `Missing API key`). | With an `apiKey`, fix it: a rejected key never falls back to anonymous access. Without one, the deployment requires a partner key: call it from a server that holds one. |
| `403`                     | The client or its access profile lacks permission for this service or protocol instance.                                                                                       | Use a key authorized for the instance and service, or none where the anonymous profile is permitted.                                                                     |
| `404` with `gatewayError` | Unknown or disabled protocol instance or service.                                                                                                                              | A **configuration** error, not an outage: fix `protocolInstance`. A `404` with the service code `NOT_FOUND` instead means the instance stores no such request.           |
| `422`                     | The service rejected the payload's shape; `validationErrors` lists each issue.                                                                                                 | A client bug: fix the request rather than retrying it.                                                                                                                   |
| `429`                     | Rate limit reached. Anonymous clients share 10 requests per second per IP and instance.                                                                                        | The SDK resends a submit up to twice, waiting `max(retryAfterMs, 1 s + jitter)`. Exhausted, it is the one transport failure that is provably not accepted.               |
| `502`                     | Upstream unavailable, **or** a protocol-instance identity mismatch — possibly after the body reached the service.                                                              | Ambiguous, never a rejection. Resend under the same key.                                                                                                                 |
| `503`                     | With the gateway envelope, its configuration is not ready — the request never left the gateway. Without it, an upstream `503` that may have been seen.                         | The envelope form is retried like a `429` and is fallback-eligible; the bare form is ambiguous.                                                                          |

`retryAfterMs` is the `Retry-After` delay in milliseconds, or `null`. In a browser it is usually `null`: a cross-origin page reads `Retry-After` only when the gateway lists it in `Access-Control-Expose-Headers`, and by default the gateway exposes only `X-GasLessQ-Protocol-Instance`. Treat `null` as unknown, never as "retry now" — the SDK's own retry waits at least a jittered second either way.

## Vendor codes

From the service itself, via `parseGaslessErrorDetail(err)?.code`:

| Code                                             | Meaning / action                                                                                                                                            |
| ------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `FEE_POLICY_WOULD_REVERT`                        | The fee or free-quota policy blocks the request; refresh the policy before rebuilding. Fallback-eligible.                                                   |
| `INSUFFICIENT_ALLOWANCE`                         | Raise the billing account's gateway allowance. Fallback-eligible.                                                                                           |
| `SIMULATION_REVERTED`                            | The relay could not execute in simulation. Inspect the decoded cause, then correct funding, authorization or payload — **never resend the same signature**. |
| `DEPOSIT_BELOW_MINIMUM`                          | Wait for funding or finality, or add collateral.                                                                                                            |
| `CHAIN_CONFIGURATION_ERROR`                      | The backend deployment is incompatible; escalate to the operators.                                                                                          |
| `CHAIN_EXECUTION_ERROR`                          | An RPC or contract call failed; inspect `rpcError` before deciding whether to retry.                                                                        |
| `IDEMPOTENCY_KEY_CONFLICT`                       | HTTP `409`: the key already belongs to another wallet selection or workflow. Mint a new key for a new action (`isGaslessIdempotencyConflictError`).         |
| `NOT_FOUND`                                      | The id or hash is not stored in the selected instance. After a `202`, expect this briefly — the accept-vs-record race.                                      |
| `INVALID_ADDRESS` / `INVALID_OPERATION_SELECTOR` | The payload named something the service will not relay.                                                                                                     |

A FastAPI schema failure returns `422` with no code at all; read `validationErrors`.
